# External SONIC reference contract: offline validation

This is the next step after [live feedback validation](/docs/platforms/humanoid/g1/sonic-feedback.md#active-planner-session-2026-10-06). DimOS can now **encode reference bytes offline** for the inspected PC2 publisher/receiver format. It does not publish them, start a controller, change its mode or execute a manipulation plan.

The implementation is sonic_reference.py (`/dimos/robot/unitree/g1/sonic_reference.py`). The last observed real session used `--input-type keyboard`; the interface audited here requires a separately commissioned `zmq_manager` session. The robot session was left unchanged.

## What is implemented

| Function | Encoded packet | Scope |
| --- | --- | --- |
| `encode_command(start=..., stop=..., planner=...)` | `command`, protocol v1, 1,290 bytes | Explicit booleans; rejects simultaneous start and stop. Both false allow mode selection without a start/stop request. |
| `encode_token_reference(token=..., left_hand=..., right_hand=..., frame_index=...)` | `pose`, protocol v4, 1,604 bytes | One 64-value latent token, signed int64 index, seven positions per hand. |

Each packet is one topic prefix, a 1,280-byte zero-padded JSON header, then ordered binary fields. Payloads use little-endian values. Both hands are mandatory in this encoder, and their slots pass through unchanged. The v4 field order and shapes are:

| Field | Type | Shape |
| --- | --- | --- |
| `token_state` | float32 | `[1, 64]` |
| `frame_index` | int64 | `[1]` |
| `left_hand_joints` | float32 | `[1, 7]` |
| `right_hand_joints` | float32 | `[1, 7]` |

Wrong lengths, booleans/strings in numeric vectors, nonfinite or overflowing float32 values, and invalid indices are rejected. This checks wire representation. It does **not** check calibrated hand limits, token validity for a policy, collisions, support conditions or end-effector accuracy. Zero tokens are not an established stationary posture. These tokens are not the Cartesian poses or joint trajectories produced in the earlier DimOS manipulation exercises.

The installed streamer's helper couples `stop = not start`. The new encoder requires all three flags explicitly so a mode-only request need not imply shutdown or startup. Both-false behavior is supported by the inspected manager's command decoder; it has not been exercised on the robot.

## Cancellation and disconnect findings

| Action/event | Installed source behavior | Consequence for our service |
| --- | --- | --- |
| `command.stop=true` | Manager sets `operator_state.stop`; main loop exits; `Stop()` joins controller threads and sends a body damping command (`kp=0`, `kd=8`, zero feedforward torque). | Controller shutdown is not a normal task pause. No holding or balanced posture is guaranteed by this path. |
| `command.planner=true`, stop false | Switches the manager to planner mode and triggers a reset. If planner is already initialized, its movement state can be retained. Otherwise it requests IDLE and waits for planner initialization, with a five-second timeout that requests stop. | Returning to planner is a handover, not proof of zero movement or completed cancellation. |
| Planner messages disappear | With planner enabled/initialized, an invalid/consumed message older than 1,000 ms leads to IDLE and clears upper-body/hand-control flags. A pending `valid` message is applied first **without checking its age**, then consumed. | The comment describing a one-second timeout is not a universal hard deadline. Clearing hand flags does not define a verified grasp-release or hold behavior. |
| v4 token publisher disappears | After a received token is consumed, the endpoint keeps its external-token and hand buffers. The no-new-data path does not clear them. The main loop can keep copying the cached token, updating its token timer. | Closing the publisher does not establish cancellation. A retained latent reference can continue driving the policy; it does not mean the robot holds still. |
| Token timeout/warning | The main source has a 200 ms token warning path when external-token availability is false; it explicitly retains the last tokens. Streaming-age monitoring also feeds an audio warning path. | Neither path establishes a command-expiry stop. The cached-token path can bypass the missing-token warning condition. |
| Repeated or older `frame_index` in v4 | The inspected v4 decoder reads it for logging and does not compare it against an accepted index. | The sender must not treat it as replay protection, acknowledgement or completion evidence. |
| Multiple commands arrive before manager update | Start/stop flags accumulate with OR; the most recent planner flag wins. There is no per-task command identifier in these packets. | A later false flag cannot withdraw an already accumulated request. PUB send completion cannot be used as controller acceptance or task completion. |

The manager forwards pose-interface hand/token data while transitioning back to planner until its readiness flag changes. We have not validated all transition timing or eventual physical hand behavior. Its planner timeout clears upper-body and hand flags, but does not clear the VR flag in that branch. These are reasons to test the complete state transition in simulation, rather than infer it from the selected mode alone.

The shutdown path's final `LowCommandWriter()` also calls the Dex3 writer. `CreateDampingCommand()` changes the body command only; it does not clear the hand targets. Thus the body damping behavior does not establish what happens to a held object.

The existing streamer's normal `--end planner` path blends its current token back toward a planner token captured at episode start, blends hand targets toward zero, and requests planner mode. Its other ending requests stop. This is an application-specific movement sequence, not a generic cancellation primitive; a grasped object makes its hand behavior especially relevant. The ending is normal sequential code, not a guaranteed process-crash cleanup path.
