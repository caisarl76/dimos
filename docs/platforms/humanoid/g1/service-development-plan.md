# G1 service development and hardware commissioning plan

Prepared on 2026-10-06 for the user's two G1 EDU robots. Repository baseline: `7529659c88c76eb4800552ad1d4fa5dd584ecc80`, plus the local walkthrough examples. This is a proposed architecture and commissioning sequence; it does not establish real-hardware readiness. After the user powered on `pc2_222`, a [read-only inventory and camera acquisition check](/docs/platforms/humanoid/g1/pc2-222-inventory-2026-10-06.md) established body/hand feedback and RGB/depth access. No controller handoff or robot motion was performed.

## First service and success criteria

User-confirmed task: on `pc2_222`, pick one object from a fixed table and place it in a tray. The user also confirmed a RealSense D435i in the default G1 EDU hardware setup. Proposed implementation: begin with one known lightweight object, a stationary robot, and one arm/hand; keep the other arm in a verified holding configuration. Add perception-based source localization after a known-pose baseline works. Add navigation after stationary manipulation is repeatable. Object dimensions, mass, grasp surface, table height, and tray position remain to be measured, so this plan specifies no grasp pose, payload allowance, or contact force.

Proposed acceptance run: 20 operator-supervised attempts with fixed initial conditions. Report success count, cycle times, interventions, drops, perception failures, and recovery outcomes. An attempt succeeds only if the object is observed inside the tray, the hand releases it, and the arm retracts. A `COMPLETED` trajectory or a finger-close command alone does not establish task success. This trial is an initial engineering baseline, not a reliability certification.

## Control architecture decision

**User-selected direction, 2026-10-06: keep the existing controller and inspect how DimOS can integrate above it.** The observed `g1_deploy_onnx_ref` deployment is the hardware baseline to preserve. A [follow-up source and launcher trace](/docs/platforms/humanoid/g1/sonic-upstream-status.md#installed-external-controller-follow-up-trace) identified an installed SONIC v1.1 workflow with ZeroMQ reference input on port 5556 and feedback on 5557. The earlier exited PID's exact executable and arguments remain unverified. The same [upstream SONIC review](/docs/platforms/humanoid/g1/sonic-upstream-status.md) found a native implementation in open PRs #4304 → #4305 → #3557, not merged into main. That implementation runs SONIC inside DimOS and owns body commands; it does not attach to the existing C++ controller. The earlier vendor-balance proposal is now an alternative, documented in the [official-interface review](/docs/platforms/humanoid/g1/control-interface-review.md).

| Route | Existing support | Decision for this project |
|---|---|---|
| Existing C++ SONIC deployment + DimOS service modules | Installed VLA launcher selects SONIC v1.1 with a ZeroMQ streamer. The user's later live session instead selected keyboard input; the new DimOS subscriber decoded its feedback and agreed closely with independent body/hand DDS positions. | User-selected direction: retain this controller. Passive telemetry now works; validate reference encoding and input/lifecycle behavior offline, then in simulation. Hardware command integration must account for the selected input mode. |
| Vendor controller + upper-body SDK + Dex3 | Unitree documents these interfaces. No `arm_sdk`/Dex3 implementation was found in the inspected local `dimos/` and `scripts/` sources. | Alternative only if the user later changes controller route; validate firmware and handoff/blending contract first. |
| DimOS GR00T whole-body controller + Dex3 | Body controller, MuJoCo backend, arm planning, and recording already compose in DimOS. Dex3 integration remains missing. | Keep as the current simulation/reference route. Real deployment requires its own whole-body-controller commissioning. |
| Native SONIC inference inside DimOS | Open upstream PR stack #4304 → #4305 → #3557; absent from the user's checkout and reviewed main. Reviewed blueprint controls 29 body joints and does not include Dex3. | Separate simulation/review candidate. Adopting it would migrate body-command ownership away from the C++ runtime; it is not the requested bridge. |

The current whole-body connection (`/dimos/robot/unitree/g1/wholebody_connection.py`) publishes `rt/lowcmd`; `release_sport_mode=True` releases the active mode at startup. Its shutdown path disables motor commands. Therefore launching or stopping this connection is a control transition, and a generic process shutdown is not a promise that standing balance continues. Setting `release_sport_mode=False` does not turn a `lowcmd` backend into an `arm_sdk` backend. The G1 teleop composition (`/dimos/robot/unitree/g1/blueprints/basic/unitree_g1_teleop.py`) uses this whole-body control family.

**2026-10-06 ownership update:** a [passive follow-up](/docs/platforms/humanoid/g1/pc2-222-inventory-2026-10-06.md#follow-up-publisher-ownership-and-time-sources) observed `g1_deploy_onnx_ref` PID `39396` on PC2 actively publishing `rt/lowcmd` and both Dex3 command topics. It exited before process inspection; the agent did not launch or stop it. The user chose to retain that controller route. The installed input and feedback formats are now traced; arbitration, hand mapping, stop/recovery behavior and the next live process's configuration still need validation. The Unitree app's robot software version is explicitly not checked yet.

For the selected external-controller route, preserve its body and hand command ownership and define how service requests enter that controller. DimOS must not add a parallel motor/hand writer as a shortcut to manipulation. The upstream native SONIC task instead claims all 29 body joints and accepts upper-body encoder hints; this differs from the simulation's independently controlled arms. Reference tracking, controller release, hold, cancellation, disconnect behavior, and measured task completion need explicit contracts on whichever route is implemented.

## Reuse and integration boundaries

The service flow will be: operator request → task state machine → object localization and arm/hand actions → observed task result. DimOS supplies module lifecycle, typed streams/RPCs, planning, recording, and later navigation. The robot adapters and the service state machine connect those pieces for this embodiment.

| Component | Reuse | Work needed |
|---|---|---|
| Arm API and planning | Arm SDK (`/dimos/manipulation/sdk.py`), ManipulationModule (`/dimos/manipulation/manipulation_module.py`), [planning groups](/docs/capabilities/manipulation/planning_groups.md) | Preserve useful group naming, but establish how planned references map to the selected controller. SONIC encoder hints do not guarantee direct joint-trajectory or Cartesian tracking; validate tracking and collision behavior before exposing existing execution semantics. |
| Hardware integration | ManipulatorAdapter (`/dimos/hardware/manipulators/spec.py`), registry (`/dimos/hardware/manipulators/registry.py`), [integration guide](/docs/capabilities/manipulation/adding_a_custom_arm.md) | Build passive `g1_debug` feedback integration on port 5557 before any reference publisher on 5556. Preserve existing motor-command ownership. Retain full 29-joint telemetry for collision checking and define state freshness/source selection. Existing manipulation execution semantics need a separately validated mapping to SONIC references. |
| Dex3 | Vendor interface evidence in the [review](/docs/platforms/humanoid/g1/control-interface-review.md) and traced streamer protocol | The C++ route takes seven targets per hand through the streamer's `pose` message. Saved runs select `dex3_right_order=dataset`; verify its conversion against physical joint names before reuse. Validate limits, stale-state handling and measured grasp verification; avoid parallel hand writers and unvalidated single-value gripper mappings. |

| Perception and obstacles | 2D detection (`/dimos/perception/detection/module2D.py`), 3D detection (`/dimos/perception/detection/module3D.py`), [xArm grasping reference](/docs/capabilities/manipulation/xarm-grasp.md) | Enable a matching simulated camera; locate the object, transform it into the planning frame, and add table/environment geometry. Keep the first service deterministic and operator-triggered. Optional `@skill` methods can later call the same bounded task API. The LLM does not replace the controller or determine whether a grasp physically succeeded.

## Commissioning sequence and evidence gates

Each row has an observable exit condition. Work can continue on models and software while hardware is unavailable; hardware-dependent rows remain unverified.

| Order | Work | Exit evidence |
|---|---|---|
| 1 | Record per-robot software, firmware, cameras, hand models, network interfaces, and current controller mode. | Separate inventory for `pc2` and `pc2_222`; all unknowns below resolved or explicitly scoped out. |
| 2 | Observe body and hand state through subscriber-only probes. | Timestamped capture showing the expected 29 body and 7+7 hand joint mappings, finite values, update rate, and no command publishers or mode changes in the probe. Discover actual hand topic names; do not assume the examples use identical state topics. |
| 3 | Confirm the selected controller contract and adapter lifecycle. | Supported mode/firmware documented; verified command ownership, startup blend, stale-feedback behavior, operator stop, and recovery procedure. Import tests alone do not pass this gate. |
| 4 | Build the selected adapters, model, and simulation composition. | Tests for joint order/sign/units, command bounds, no-motion connection, explicit activation, stale state, cancellation, and disconnect; model/camera frame checks and a simulated blocked-path test. |
| 5 | Commission small unloaded arm motions, then each hand, under local supervision. | Measured response and stopping behavior match the command contract. Neither a DDS writer success nor a nominal execution status substitutes for feedback. Hardware procedure must match the selected route; the existing whole-body startup instructions are not reused for vendor control. |
| 6 | Execute a known-pose stationary grasp/place sequence. | Observable grasp, lift, release, placement, and retraction; clear manual recovery when verification fails. Match contact behavior to the chosen object. |
| 7 | Add perception and run the acceptance trials. | Calibrated object poses, confidence/staleness handling, collision scene, complete recordings, and the 20-attempt results table. |
| 8 | Add navigation and service deployment. | Goal cancellation and stationary manipulation transitions work; task IDs, results, logs, bounded retries, operator intervention, and restart behavior are exercised. |

Suggested task states are `READY`, `LOCALIZING`, `APPROACHING`, `GRASPING`, `VERIFYING_GRASP`, `TRANSFERRING`, `RELEASING`, `VERIFYING_PLACE`, and `RETRACTING`, with terminal `SUCCEEDED`, `CANCELLED`, or `FAULT`. Failed or stale verification stops progression. A communication timeout requires determining the actual controller state before another motion; never automatically replay a timed-out command.
