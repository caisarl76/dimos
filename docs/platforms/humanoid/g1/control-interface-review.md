# G1 control interface review

Reviewed 2026-10-06 against official Unitree source and documentation. Links to `main`/`master` describe the reviewed upstream implementation; they do not establish the software installed on either robot. No robot was contacted or commanded during this review.

**Recommendation:** for the first stationary manipulation service, qualify Unitree locomotion plus `rt/arm_sdk` first. Let the vendor controller maintain balance, initially expose only the 14 arm joints, and use a separate Dex3 interface on the equipped robot. This recommendation follows Unitree's documented coexistence model; it remains conditional on installed firmware, operating mode, and measured behavior. The motion-mode wiki itself says this path has not received large-scale testing. [Official motion-mode explanation](https://github.com/unitreerobotics/xr_teleoperate/wiki/Motion)

User-provided inventory: `pc2` (`192.168.0.223`) has 29 body joints and no hands; `pc2_222` (`192.168.0.222`) has 29 body joints plus two Dex3 hands. Both were last reported off when this upstream review was prepared. A subsequent [powered-on `.222` inventory](/docs/platforms/humanoid/g1/pc2-222-inventory-2026-10-06.md) verified body/hand telemetry, both Dex3 state-topic families, camera acquisition, and the installed SDK/API differences. It did not test motion or establish firmware compatibility.

Retain vendor balance and establish one arm-command owner. |

**Verified arm interface facts.** The official C++ and Python `g1_arm7_sdk_dds_example` publish `unitree_hg::LowCmd_` on `rt/arm_sdk`, observe `LowState_` on `rt/lowstate`, and command joint positions with `dq`, feed-forward `tau`, `kp`, and `kd`. Their joint lists contain both seven-joint arms **and three waist joints**. The Python mapping places arms at indices 15–28 and the blend/control weight at `motor_cmd[29].q`; index 29 is a protocol slot, not another physical body joint. [C++ arm7 example](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2/main/example/g1/high_level/g1_arm7_sdk_dds_example.cpp), [Python arm7 example](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/example/g1/high_level/g1_arm7_sdk_dds_example.py)

The examples supply joint targets, not a Cartesian planner, inverse-kinematics service, collision checker, or grasp policy. Their 20 ms example period and gains are example settings, not certified timing or stability limits. The Python source explicitly marks waist pitch/roll invalid on configurations with a locked waist. Therefore, 29 physical joints do not prove that every joint is commandable through the current vendor mode. [Python arm7 example](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/example/g1/high_level/g1_arm7_sdk_dds_example.py)

The wiki describes blending the vendor arm command with the user command as weight changes between zero and one, and recommends gradual weight changes when target poses differ. Recommendation: qualify takeover from measured joint positions and a bounded release to the vendor pose; do not treat process termination as a proven handback. Leave waist control out of the initial service until the installed mode's contract is verified. [Motion wiki](https://github.com/unitreerobotics/xr_teleoperate/wiki/Motion)

**Locomotion and ownership.** SDK2 Python `LocoClient` offers `GetFsmId`, velocity commands, balance/height setters, canned arm tasks, and explicit `SwitchToUserCtrl` / `SwitchToInternalCtrl` calls. Internal return modes are `LAST`, `PASSIVE`, and `WALKRUN`. These methods prove client-side API availability, not support on every G1 firmware. Do not assume the explicit user-controller API is interchangeable with `MotionSwitcherClient.ReleaseMode()` or required for `arm_sdk`. [Python LocoClient](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/unitree_sdk2py/g1/loco/g1_loco_client.py)

`StopMove()` sends zero velocity; `Damp()` changes the FSM. They are different operations, and neither alone specifies an arm/hand recovery sequence. Several Python convenience methods discard the underlying return code; an adapter needing an acknowledgement should inspect the called API's result and subsequent state. [Python LocoClient](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/unitree_sdk2py/g1/loco/g1_loco_client.py)

Initialization must be audited per class: the official low-level example's `Custom.Init()` calls `ReleaseMode()` until the existing controller name clears; XR's `G1_29_ArmController` constructor starts a command-publishing thread. Neither is an observation-only probe. Establish telemetry through a dedicated subscriber before constructing a motion-owning adapter. [Low-level initialization](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2_python/master/example/g1/low_level/g1_low_level_example.py), [XR arm constructor](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/robot_control/robot_arm.py)

Recommendation: enforce one body-control regime per robot. Within the vendor regime, allow one arm SDK writer; within a custom regime, route arm requests through the full-body owner. Give each hand one command writer. A stationary request means no commanded walking, not frozen balance joints. Ownership changes and disconnect behavior require explicit tests on the selected controller.

**Dex3 remains separate.** The current XR implementation uses seven motors per hand, `HandCmd_` / `HandState_`, and these topics: `rt/dex3/left/cmd`, `rt/dex3/right/cmd`, `rt/dex3/left/state`, `rt/dex3/right/state`. Its command mode packs motor ID, status, and timeout bits; demonstrated operation uses status `0x01` with position targets, gains, and zero feed-forward torque. This establishes a demonstrated joint-control path, not a complete supported-mode catalogue or a verified force-control/grasp API. [Official XR Dex3 controller](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/robot_control/robot_hand_unitree.py)

There is an upstream discrepancy: the C++ Dex3 example selects `rt/lf/dex3/left/state` or `rt/lf/dex3/right/state` at runtime, while retaining `rt/dex3/.../cmd`. Confirm the live state topic and compatible message definition on `.222`. That example also has different left/right joint limits and enters a rotation demo automatically; running it is not a passive connection test. Its stop routine sets timeout and zero gains, which must not be presumed to preserve a grasp. [SDK2 Dex3 example](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2/main/example/g1/dex3/g1_dex3_example.cpp)

The newer `rt/hand_sdk` example uses `unitree_go::MotorCmds_`, four motors, a different weight encoding, and torque-based open/close commands. It is not evidence that the seven-motor-per-hand Dex3 interface can be replaced by `rt/hand_sdk`. [Official hand SDK example](https://raw.githubusercontent.com/unitreerobotics/unitree_sdk2/main/example/g1/high_level/g1_hand_sdk_example.cpp)

Recommendation: `.223` should advertise arm reaching only; `.222` can add independently qualified hand capabilities. Hand commands and telemetry must not be appended to the 29-body-joint packet. Grasp success needs object/contact evidence beyond successful publication of a finger target.

**XR compatibility boundaries.** `--motion` is documented for G1 Regular mode (`R1+X`), excluding Running mode (`R2+A`). The current program permits Dex3 with hand tracking but rejects Dex3 with controller tracking; it separately rejects `dex1_internal` together with `--motion`. These are current application restrictions, not a universal claim about the hardware. [Official README](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/README.md), [CLI and validation](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/teleop_hand_and_arm.py)

Without `--motion`, XR invokes its debug-mode switcher, which actively releases the existing motion mode. Its G1 arm controller publishes `rt/lowcmd` in debug mode and `rt/arm_sdk` in motion mode. Thus an XR launch can change controller ownership before the operator presses the tracking-start key. [Mode selection](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/teleop_hand_and_arm.py), [switcher](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/utils/motion_switcher.py), [arm transport selection](https://raw.githubusercontent.com/unitreerobotics/xr_teleoperate/main/teleop/robot_control/robot_arm.py)

**DimOS integration implication.** Project inspection supplied by the main review found a custom full-body writer, startup sport-mode release, and shutdown that disables all 29 body motors; no implemented arm SDK or Dex3 adapter was identified. Consequently, selecting an existing DimOS blueprint does not establish vendor-control compatibility. Integration must replace the body ownership/lifecycle path deliberately, retain all measured body joints for planning, restrict eligible arm writes, and add hand-specific control where present. This is a local integration assessment, not an upstream Unitree guarantee.

**Unresolved without hardware:** installed motion/hand firmware and SDK revisions; the active FSM and waist configuration; arm SDK acceptance and actual handback behavior; user/internal-switch support; packet-loss and process-exit behavior; hand state topic availability; joint ordering, calibration, usable limits, and timeout behavior; balance under reach/payload/contact; remote-stop behavior and controller recovery. MuJoCo success does not establish these properties. Qualify them on the selected robot before describing this service as hardware-ready.

Source verification: the linked GitHub/raw source pages were readable during this review. Linked Unitree support-portal pages could not be fetched, so no portal-only claim or firmware version guarantee is made here.
