# Two-G1 synchronized SONIC arm skills: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One workstation DimOS process drives the SONIC arm skills of G1s 222 and 223. Each skill takes `robot` = `"222"`, `"223"` or `"both"`, and `both` starts the two motions within 0.5 s of each other.

**Architecture:** This builds on the Tier-1 arm engine (keyframe plans, background skills with `stop_arm`, `perform_gesture`). Task 1 is a small core change that lets a module ref be remapped to a named instance. Task 2 pulls the per-robot state and streaming out of `SonicArmSkillContainer` into a `SonicArm` engine. Task 3 starts several engines together: all prepared first, then a barrier in front of the first chunk, then a shared smooth retreat. Task 4 adds a dual container bound to two named `SonicExecutionModule` instances (`g1_222`, `g1_223`).

**Tech Stack:** Python 3.12, DimOS modules/blueprints, ZeroMQ, numpy, pytest, MuJoCo stand-in (`sonic_sim_peer`).

## Review Focus

1. **One robot never arms in `both`** (start_task refused, or the session never reaches `waiting_for_chunk`): the other must not move. Its task is cancelled before any chunk, and the result names the robot. Tests: Task 3 `test_both_peer_never_arms_moves_neither` (injected after preparation, deterministic) and `test_both_stale_feedback_refuses_before_sending` (preflight).

3. **Swapped feedback wiring** (222's telemetry reaching 223's watch) silently breaks the envelope checks. Test: Task 4 `test_dual_blueprint_wires_each_robot_to_its_own_execution`.
4. **Single-robot command while the other robot is down**: `robot="222"` must run with 223 not ready. Test: Task 4 `test_single_robot_command_ignores_the_other_robot`.
5. **Mixed outcome** (one robot fails after its stream returned `"finished"`, for example handback unconfirmed, while the other is still moving): the still-moving robot retreats, and the update reports a failure naming both, never success. Test: Task 3 `test_both_mixed_outcome_retreats_peer_and_fails_naming_both`.

7. **One robot's first chunk is rejected after the barrier** (shape, finiteness, token bound): it must be caught before anything is sent. Test: Task 3 `test_both_invalid_chunk_refused_before_sending`.

**Interfaces:**
- Produces, in `sonic_arm_skill.py`:
  - `class SonicArm: __init__(self, name: str, config: SonicArmSkillConfig, execution: SonicArmExecutionSpec, encoder: SonicEncoder, checker: ArmCollisionChecker | None)`.
    - It owns `_lock`, `_watch`, `stop: threading.Event`, and Tier-1's `_move` / `_stream` / `_task` / `_wait_done`.
    - `handle_feedback(self, feedback: SonicFeedback) -> None` is moved from the container.
    - `prepare(self, label: str, keyframes_of: Callable[[NDArray[np.float64]], list[Keyframe]], allowed: NDArray[np.float64], *, require_check: bool, report_extra: Callable[[NDArray[np.float64]], dict[str, Any]] | None = None) -> _Prepared` covers everything `_move` does before `start_task`: readiness, feedback, plan, path checks, encodes, the moved-while-encoding check, profile prechecks and the stop-during-encoding check.   - In `dimos/robot/unitree/g1/sonic_session.py`: the body of `SonicTaskSession._actions` (shape `[1..1000, 78]`, numeric, finite float32, token bound) becomes a module-level `validate_actions(values: NDArray[Any], token_bound: float) -> NDArray[np.float64]`. `_actions` calls it, with the same messages. The arm engine uses it, so a chunk the session would reject is refused while nothing has been sent.
    - `execute(self, prepared: _Prepared) -> SkillResult` covers everything from `start_task` on, with the same messages and report.
  - `SonicArmSkillContainer`:
    - `start()` builds `self._arm = SonicArm("g1", self.config, self._execution, encoder, checker)`;
    - `_run(...)` keeps its Tier-1 signature and returns `self._arm.execute(self._arm.prepare(...))`;

    - `handle_feedback` delegates. `_launch` and `_busy` stay on the container.

    2. Call `reset()` on each selected arm **after** acquiring `_busy` and **before** starting the thread. A `stop_arm` that arrives once the thread runs is kept, because nothing clears `stop` after this point.
    3. In the thread's `finally`, call `clear_watch()` on each selected arm, then release `_busy` and `stop_tool`.

    `stop_arm` only sets `stop` when `_busy` is held. In the single container, `arms` is `[self._arm]`.

### Task 3: Start several arms together

**Files:**
- Modify: `dimos/robot/unitree/g1/sonic_arm_skill.py` (`SonicArm`, `_Watch`, `_stream`; add `run_arms`)
- Create: `dimos/robot/unitree/g1/test_sonic_arm_group.py`, plus `dimos/robot/unitree/g1/conftest.py` if fixtures are shared with Task 4

**Interfaces:**
- Consumes: Task 2's `SonicArm.prepare` / `execute`.
- Produces: `run_arms(jobs: Sequence[tuple[SonicArm, Callable[[], _Prepared]]]) -> SkillResult`. Each job is a no-argument call to that arm's `prepare(...)`.
  1. Run every prepare **before any `start_task`**. Then `recheck` **every** arm, because each one's pose may have moved while a later arm was encoding. If any prepare or recheck raises, raise `RuntimeError(f"{name}: {exc}; nothing sent to any robot")`.
  2. Run each `execute` in its own thread with shared group state: a `threading.Barrier(len(jobs))` and the peer arms.
     - After its task reaches `waiting_for_chunk`, each arm calls `barrier.wait(timeout=profile["first_chunk_timeout"] / 2)`, then submits chunk 0.
     - On `BrokenBarrierError`, or if the arm itself never arms (it calls `barrier.abort()`), it cancels its own task without sending a chunk. Outcome text: `"another robot did not arm"`, or the existing `"stream did not arm (…)"`.
     - A single arm (Task 2's path) has no barrier.
  3. Onset measurement:
     - Times come from `feedback.received_monotonic`, which the execution module stamps when the ZMQ sample arrives (system-wide `CLOCK_MONOTONIC`, comparable across worker processes on one host). Never use the handler's own `time.monotonic()`: queued samples and callback delay would distort it.
     - `_Watch` gains:
       - `send_at: float | None`: `time.monotonic()` taken immediately **before** the chunk-0 `submit_chunk` call;
       - `ack_at: float | None`: taken immediately **after** that call returns;
       - `onset_q`: the `body_q` of the latest sample with `received_monotonic <= send_at`.
     - `moved_at: float | None` is the `received_monotonic` of the first sample with `received_monotonic > send_at` in which any joint of the planned displacement differs from `onset_q` by ≥ `_ONSET_RAD = 0.03` rad. This absolute threshold sits above sensor noise and idle drift.
     - The result schema for ≥ 2 arms: `metadata = {"222": report, "223": report, "submit_skew_s": float, "start_skew_s": float | None}`. `submit_skew_s` is the difference of the two `send_at` values, rounded to 3 decimals. `start_skew_s` is the difference of the two `moved_at` values, or `None` if either robot never moved. Each report also carries its own `send_at`, `ack_at` and `moved_at`, relative to the earliest `send_at`. Acceptance is on `start_skew_s`. Both robots get the same 2 s token blend before motion, so onset is comparable.
  4. Peer aborts: in `_stream`, an arm treats a peer's `watch.abort` like its own envelope abort, recording `"{peer name}: {abort}"`, and takes the Tier-1 retreat. An arm signals its peers on **any non-success across its whole `execute`**, not only a stream outcome: a stream outcome other than `"finished"`, handback unconfirmed, a session outcome other than finished, or an exception. It does this by setting its own `watch.abort` (if unset) to that reason. A peer still streaming then retreats; a peer that already finished is unaffected.
  5. Result: if every arm returned, one `SkillResult` with message `"222: <msg>; 223: <msg>"` and the metadata schema in item 3. Both skews are logged. If any arm raised, raise `RuntimeError` joining every arm's `"<name>: <message or error>"`.

Tests use two `ScriptedPeer`s and two `SonicExecutionModule`s (the `execution_config` / `execution` fixture pattern, twice) with the Tier-1 fixture patches (`keyframe_plan` wrapper, `token_schedule`, `FakeEncoder`), and one feeder thread per arm.
